# v0.4.0 implementation plan — PR by PR

Concrete sequencing for the 13 phases declared in the design plan.
Each phase = one PR, scoped so it lands independently and the engine
keeps compiling throughout. Dependencies are stated explicitly so
parallel work is possible.

## Dependency graph

```
P0 (Migration runbook — doc work) ─────────┐
                                            ↓
P1 (Fact rework + NewEvent shape) ─┐
 └─→ P1.5 (Ephemeral events decision)
      ↓
      ├─→ P2 (Aggregate + Apply<F>)
      │    └─→ P6 (Aggregator::for_type + with_aggregators)
      │         └─→ P7 (Bulk variants) ─┐
      ├─→ P3 (Projector rename)         │
      │    └─→ P4 (GROUP_NAME consts) ──┤
      ├─→ P5 (Engine::emit builder)     │
      └─→ P11 (Legacy collapse) ←───────┴── after P1..P9
           └─→ P10 (Prelude trim) + P12 (Rootsignal migration) ←── P0 runbook here
                └─→ P13 (Release)

P8 (CheckpointStore inversion) — independent, can run any time
P9 (Engine features) — after P11 (uses cleaned-up Engine surface)
```

P0 unblocks P12 (Rootsignal migration). P1 unblocks everything else.
P2/P3/P5 are independent and can run in parallel after P1.5.
P11 (the big legacy delete) waits for P1-P9 to land so it can remove
their predecessors cleanly.

## P0 — Migration runbook (doc + script)

**Scope:** Draft a complete migration runbook for rootsignal moving
from v0.3 log data to v0.4 format. Pure documentation + SQL scripts
phase — no causal-rs code changes. Lands before P12 (rootsignal
migration) executes; ideally before P1 starts so the migration shape
informs the implementation.

**Deliverables:**
- `docs/migrations/v0.3-to-v0.4-rootsignal.md` — runbook
- `scripts/migrate_v04.sql` — idempotent SQL migration in stages
- `scripts/migrate_v04_verify.sql` — verification queries
- `scripts/migrate_v04_rollback.sql` — pre-Stage-5 reversal

**Contents (runbook):**

1. **Per-Fact mapping table.** For each Fact enum in rootsignal,
   document: old `type_prefix`, old `category` per variant (if
   diverged), new `CATEGORY`, new `name()` mapping. ~15 rows.
2. **SQL migration script.** Stages:
   - Stage 1: Stop consumers
   - Stage 2: Rewrite `events.event_type` (per the Fact mapping)
   - Stage 3: Rewrite `events.aggregate_type` (category renames —
     LifecycleEvent + ScrapeEvent split, SchedulingEvent split)
   - Stage 4: Verify (queries below)
   - Stage 5: Deploy v0.4 code
   - Stage 6: Restart consumers
3. **Verification queries.** Distinct `(event_type, aggregate_type)`
   pairs should match v0.4 expected list exactly.
4. **Rollback procedure.** Reverse the UPDATEs if anything goes
   wrong before Stage 5. After Stage 5, rollback means re-deploying
   v0.3 code, which still reads the new format if Stage 2 ran (so
   really only safe rollback window is before Stage 2).
5. **Cursor continuity test fixture.** Integration test that runs
   the migration on a fixture log, then verifies a v0.4 consumer
   resumes from the cursor with no replay and no skip.

**Acceptance criteria:**
- Runbook reviewed against rootsignal's actual Fact set
- Migration script runs idempotently on a copy of staging data
- Verification queries pass after migration; fail before
- Cursor continuity test passes

**Risk:** the Fact mapping table needs to be exhaustive — missing a
fact means events in the wrong format post-migration. Mitigate with
explicit verification that every Fact in `rootsignal-scout::events`
is covered.

**Estimated effort:** 1 day.

## P1 — Fact trait rework + NewEvent shape

**Scope:** Replace `type_name`/`type_prefix`/`stream() -> StreamRef`
on Fact with the v0.4 shape: `CATEGORY` const + `name()` + `stream_id()`.
**Also rename `NewEvent` shape** (F2.6 finding): `aggregate_type:
Option<String>` → `category: String` (required), `aggregate_id:
Option<Uuid>` → `stream_id: Uuid` (required). The Kurrent backend
composes stream names directly from these fields.

Update the `#[fact]` macro to generate the new shape. Update backend
code that reads stream identifiers.

**Files:**
- `modules/causal/src/fact.rs` — trait def
- `modules/causal_core_macros/src/fact.rs` — `#[fact]` macro impl
- `modules/causal/src/engine_v3.rs` — uses of `Fact::stream()` change
  to `format!("{}-{}", F::CATEGORY, f.stream_id())`
- `modules/causal/src/types.rs` — drop `StreamRef`, rename NewEvent fields
- `modules/causal/src/lib.rs` — drop `StreamRef` re-export
- `modules/causal/src/memory_store.rs` — update NewEvent field reads
- `modules/causal/src/projection_runner.rs`, `reactor_runner.rs`,
  `multi_projector.rs` — any NewEvent construction or reads
- `modules/causal/tests/*` — Fact impls in test fixtures
- `modules/causal_replay/src/stream.rs` — any stream-name composition
- `modules/causal_replay/src/pointer.rs` — backend impl updates

**Trait change:**

```rust
// Before:
pub trait Fact {
    fn type_name(&self) -> &str;
    fn type_prefix() -> &'static str;
    fn stream(&self) -> StreamRef;
    fn occurred_at(&self) -> Option<DateTime<Utc>> { None }
}
pub struct StreamRef { pub category: &'static str, pub id: Uuid }

// After:
pub trait Fact {
    const CATEGORY: &'static str;
    fn name(&self) -> &str;
    fn stream_id(&self) -> Uuid;
    fn occurred_at(&self) -> Option<DateTime<Utc>> { None }
}
```

**Stored event_type composition:** the runtime composes
`event_type = format!("{}:{}", F::CATEGORY, fact.name())` at emit
time and stores it in `PersistedEvent.event_type`. Deserialization
goes the other way — read the stored event_type, split on `:`,
match category to find the right Fact codec.

**Macro updates:** `#[fact]` (formerly `#[event]`) generates the
trait impl. Strip the `:` prefix from variant names if present;
emit the bare name. Generate `CATEGORY` from the macro attribute:

```rust
#[fact(category = "schedule")]
pub enum ScheduleEvent {
    Created { schedule_id: Uuid, /* ... */ },
}
// generates:
impl Fact for ScheduleEvent {
    const CATEGORY: &'static str = "schedule";
    fn name(&self) -> &str {
        match self {
            Self::Created { .. } => "created",
            /* ... */
        }
    }
    /* stream_id derived from #[stream_id] field attr or first Uuid field */
}
```

**Acceptance criteria:**
- All in-crate Fact impls compile under new shape
- `#[fact]` macro generates the new shape for both the old `prefix`
  and new `category` syntax (gradual deprecation path)
- All existing tests pass
- New test: composition round-trip — emit a Fact, read it back, get
  the same category + name + stream_id

**Risk:** stored event_type format changes. Pre-existing log data
has events stored as `"category:name"` (the current format). The
new composition produces the same string format, so reading is
backward-compatible. Verify this in a test.

**Estimated effort:** 2 days (was 1; expanded for NewEvent rename
+ backend churn).

## P1.5 — Ephemeral events decision

**Scope:** Decide what happens to ephemeral events (`NewEvent::persistent:
bool = false` in v0.3) under v0.4. The v0.4 Fact trait requires
`stream_id: Uuid`, implying every fact has a stream. Ephemerals
(in-process signaling, no log, no stream) don't fit.

**Pre-work:** audit rootsignal for ephemeral usage. Today the
`persistent` flag exists; need to know if and where it's set to
false.

```bash
grep -rn "ephemeral\|persistent: false" rootsignal/modules/rootsignal-scout/src/
```

**Three options:**

**(a) Drop ephemerals entirely.** All facts are persistent. In-process
signaling moves to `deps + Arc<Mutex>` or direct function calls.
Simplest API. Audit determines if this breaks anything significant.

**(b) Keep ephemerals via `.ephemeral()` builder.**
`engine.emit(fact).ephemeral().await?` skips the log. Single Fact
trait, optional persistence. Two-mode complexity.

**(c) Separate `Signal` trait.** Distinct from `Fact`. Different
emit path. Clean but more API surface.

**Recommended default: (a).** Lowest API complexity, most aligned
with "everything is a fact" mental model. Contingent on audit
showing rootsignal can absorb the change.

**Deliverables:**
- Decision documented in this plan (update D# tally if a new
  decision is added)
- Rootsignal audit results pasted into the implementation PR
- `NewEvent` struct lands with or without `persistent: bool` based
  on decision

**Acceptance criteria:**
- Decision recorded with reasoning
- All in-crate ephemeral-using tests updated to fit the chosen
  option
- Rootsignal's ephemeral sites identified (handled in P12)

**Estimated effort:** 0.5 day (decision + audit + code adjustment).

## P2 — Aggregate marker + Apply<F> extension

**Scope:** Replace the legacy `Aggregate::aggregate_type()` method with a
marker trait. Introduce `Apply<F: Fact>` extension trait for fold
behavior. Update `AggregatorRegistry` to dispatch by `(aggregate_type,
fact_type)` rather than the legacy `(aggregate_type, event_prefix)`.

**Files:**
- `modules/causal/src/aggregator.rs` — both trait defs
- `modules/causal/src/aggregate_v3.rs` — delete (folded into
  aggregator.rs since the new shape is unified)
- `modules/causal/src/lib.rs` — re-exports
- `modules/causal/src/contexts.rs` — `Ctx::aggregate*` accessors
  now bound on the marker `Aggregate` (no method requirement on the
  trait)
- `modules/causal_core_macros/src/aggregator.rs` — macros generate
  Apply<F> impls per event handler

**Trait change:**

```rust
// Before (legacy):
pub trait Aggregate: Default + Clone + Send + Sync + 'static {
    fn aggregate_type() -> &'static str;
}
pub trait Apply<E> {
    fn apply(&mut self, event: E);
}

// After:
pub trait Aggregate: Default + Send + Sync + 'static {}
pub trait Apply<F: Fact>: Aggregate {
    fn apply(&mut self, fact: &F);
}
```

Note `&F` (borrowed) replaces `E` (owned). Production already uses
references through the registry path; the trait now reflects that.

**Registry dispatch:** the existing `AggregatorRegistry` keys by
`(aggregate_type_id, fact_type_id)`. With marker trait, the
`aggregate_type` is the Rust `TypeId::of::<A>()`. With `Apply<F>`,
the `fact_type` is `TypeId::of::<F>()`. Same dispatch mechanism,
cleaner types.

**Macro update:** `#[aggregators]` generates an `aggregators() -> Vec<Aggregator>`
fn where each `Aggregator` value is constructed via the new
`Aggregator::for_apply::<A, F>()` constructor (one per `Apply<F>`
impl).

**Engine.load signature:**

```rust
pub async fn load<A, F>(&self, id: Uuid) -> Result<(A, StreamVersion)>
where
    A: Aggregate + Apply<F>,
    F: Fact;
```

Caller specifies both types:
```rust
let (schedule, version) = engine.load::<Schedule, ScheduleEvent>(id).await?;
```

Two type params is the cost of multi-Fact-permitted Aggregate. Could
be cleaned up later with a `LoadableAggregate` blanket impl if
ergonomics suffer.

**Acceptance criteria:**
- Multi-Fact aggregate (PipelineState in test fixtures) compiles and
  folds correctly
- Single-Fact aggregate (Schedule, Counter) compiles, `engine.load`
  works
- `ctx.aggregate::<X>()` and `ctx.aggregate_of::<X>(id)` work for
  both single-Apply and multi-Apply aggregates
- All v3 aggregate tests pass

**Risk:** Apply<F> orphan rule — users may want to implement
Apply<F> for a foreign type/fact combo. Standard Rust orphan rules
apply. Document.

**Estimated effort:** 1 day.

## P5 — Engine::emit builder collapse

**Scope:** Replace `Engine::emit`, `emit_in`, `append`, `append_in`
with one `Engine::emit` method that returns an `EmitBuilder`. CAS
via `.expecting(v)`. Per-emit metadata via `.metadata(k, v)`. Delete
`WriteOptions`.

**Files:**
- `modules/causal/src/engine_v3.rs` — Engine impl, builder struct
- `modules/causal/src/lib.rs` — drop `WriteOptions` from prelude
- All callers within causal (tests, examples) — update emit call
  sites

**API:**

```rust
impl Engine {
    pub fn emit(&self, input: impl Into<EmitInput>) -> EmitBuilder<'_>;
    // Other methods unchanged (load, await_observed_by, shutdown)
}

pub struct EmitBuilder<'a> {
    engine: &'a Engine,
    input: EmitInput,
    expected: Option<StreamVersion>,
    metadata: Metadata,
}

impl<'a> EmitBuilder<'a> {
    pub fn expecting(mut self, version: StreamVersion) -> Self {
        self.expected = Some(version); self
    }
    pub fn metadata(mut self, key: &str, value: impl Into<serde_json::Value>) -> Self {
        self.metadata.insert(key.into(), value.into()); self
    }
}

impl<'a> IntoFuture for EmitBuilder<'a> {
    type Output = Result<LogCursor>;
    type IntoFuture = /* boxed future */;
    fn into_future(self) -> Self::IntoFuture { /* actual emit */ }
}

pub enum EmitInput {
    One(Box<dyn FactErased>),
    Many(Vec<Box<dyn FactErased>>),
}

impl<F: Fact> From<F> for EmitInput { /* wraps as One */ }
impl<F: Fact> From<Vec<F>> for EmitInput { /* wraps as Many */ }
```

The `FactErased` is an internal type-erased view of Fact for the
input enum to avoid making `EmitInput` generic.

**Acceptance criteria:**
- `engine.emit(fact).await?` works
- `engine.emit(fact).expecting(v).await?` does CAS, errors on
  conflict
- `engine.emit(vec![f1, f2]).expecting(v).await?` batch-writes
- Engine-level metadata defaults merge with per-emit overrides
- No `emit_in`, `append`, `append_in`, `WriteOptions` remain

**Risk:** the `Into<EmitInput>` plus `IntoFuture` plus generic Fact
combination may hit type-inference issues with certain Fact enums.
Standard mitigation: explicit turbofish at call sites that confuse
the compiler.

**Estimated effort:** 1 day.

## P6 — Aggregator::for_type and unified with_aggregators

**Scope:** Drop `EngineBuilder::with_aggregate<A>` (singular). Add
`Aggregator::for_type::<A>()` constructor that produces a type-
erased value from `Aggregate + Apply<F>` impls. `with_aggregators(I)`
becomes the only registration method, taking an `IntoIterator<Item = Aggregator>`.

**Files:**
- `modules/causal/src/aggregator.rs` — `Aggregator::for_type` impl
- `modules/causal/src/engine_v3.rs` — drop `with_aggregate`,
  consolidate to `with_aggregators` for both write-OCC marker and
  read-fold registration
- `modules/causal_core_macros/src/aggregators.rs` — macro generates
  `for_type::<A>()` calls

**API:**

```rust
impl Aggregator {
    /// Construct a type-erased Aggregator value for a type that
    /// implements Aggregate + Apply<F> for one or more F. Looks up
    /// all Apply impls via TypeId reflection at registration time.
    pub fn for_type<A: Aggregate + AnyApply + 'static>() -> Aggregator;
}
```

`AnyApply` is an internal marker that allows the constructor to
enumerate all Apply impls on A. Implementation via macro is
straightforward; doing it manually requires listing every Apply<F>
explicitly — which is fine for users not using the macro.

**Builder:**

```rust
EngineBuilder::new(/* ... */)
    .with_aggregators([
        Aggregator::for_type::<Schedule>(),
        Aggregator::for_type::<PipelineState>(),
    ])
    .with_aggregators(my_module::aggregators())  // chainable
```

**Acceptance criteria:**
- Single-Apply aggregate registers via `Aggregator::for_type`
- Multi-Apply aggregate registers and dispatches correctly
- `with_aggregate<A>` singular is deleted
- All existing aggregator tests pass

**Risk:** the `for_type` constructor needs to enumerate Apply<F>
impls at compile time. This requires either macro generation (the
`#[aggregator]` macro) or a manual `inventory`-style registration.
Decide based on what's cleanest. The macro path is preferred.

**Estimated effort:** 1 day.

## P7 — Bulk registration variants

**Scope:** Add `with_projectors(I)`, `with_multi_projectors(I)`,
`with_reactors(I)` bulk variants matching the macro-output
convention (`module::projectors()` returning `Vec<Box<dyn ProjectorRegistration>>`).

**Files:**
- `modules/causal/src/engine_v3.rs` — add three bulk methods
- `modules/causal_core_macros/src/{projectors,reactors}.rs` —
  macros emit registration vectors

**API:**

```rust
pub trait ProjectorRegistration: Send + 'static {
    fn register(self: Box<Self>, builder: EngineBuilder) -> EngineBuilder;
}

impl<P: Projector + 'static> ProjectorRegistration for P {
    fn register(self: Box<Self>, builder: EngineBuilder) -> EngineBuilder {
        builder.with_projector(*self)
    }
}

impl EngineBuilder {
    pub fn with_projectors<I>(mut self, ps: I) -> Self
    where I: IntoIterator<Item = Box<dyn ProjectorRegistration>>
    {
        for p in ps { self = p.register(self); }
        self
    }
}
```

Same pattern for Reactor and MultiProjector.

**Macro usage:**

```rust
#[projectors]
pub mod schedules {
    use super::*;
    pub fn projectors() -> Vec<Box<dyn ProjectorRegistration>> {
        vec![
            Box::new(SchedulesProjector::new(...)),
            Box::new(ScheduledScrapesProjector::new(...)),
        ]
    }
}

// In builder:
.with_projectors(schedules::projectors())
```

**Acceptance criteria:**
- Bulk registration works for all three trait families
- Order is preserved (registration happens in iteration order)
- Single + bulk can be chained freely

**Risk:** low. Mechanical addition.

**Estimated effort:** 1 day.

## P9 — Engine features (on_dlq, default_metadata, snapshot_every)

**Scope:** Add `on_dlq(mapper)`, `with_default_metadata(json)`, and
`snapshot_every(N)` to `EngineBuilder`. Drop `with_store` shorthand
(if it exists in v3 — verify).

**Files:**
- `modules/causal/src/engine_v3.rs` — builder methods + engine
  internal hooks
- `modules/causal/src/projection_runner.rs` / `reactor_runner.rs` —
  DLQ mapper integration on terminal failure
- `modules/causal/src/lib.rs` — re-export `DlqInfo`

**API:**

```rust
pub struct DlqInfo {
    pub group_name: String,
    pub source_event_id: Uuid,
    pub source_event_type: String,
    pub error: String,
    pub attempts: u32,
}

impl EngineBuilder {
    pub fn with_default_metadata(mut self, defaults: serde_json::Value) -> Self;

    pub fn snapshot_every(mut self, n: u32) -> Self;

    pub fn on_dlq<F, Out>(mut self, mapper: F) -> Self
    where
        F: Fn(DlqInfo) -> Option<Out> + Send + Sync + 'static,
        Out: Fact;
}
```

**Implementation notes:**

- `with_default_metadata`: store on EngineBuilder; pass to emit
  builder construction; merge with per-emit metadata at emit time
- `snapshot_every`: store on EngineBuilder; the
  `AggregatorRegistry::apply_event` method already knows per-aggregate
  version; the engine compares version-since-last-snapshot to N and
  triggers `SnapshotStore::save` when threshold hit. Only fires for
  single-Apply aggregates (multi-Apply aggregates aren't backed by
  one stream and don't snapshot meaningfully).
- `on_dlq`: store the mapper as `Arc<dyn Fn(DlqInfo) -> Option<EmittedFact>>`.
  When a `ReactorRunner` exhausts retries on a reactor, call the
  mapper; if it returns Some, write the result through the same
  outbox path the reactor would have used.

**Acceptance criteria:**
- Tests for each: metadata round-trips, snapshot triggers at
  threshold, on_dlq emits the mapped fact when a reactor hits its
  retry cap
- Backwards compat: existing engine builds without these methods
  continue to work (defaults: no metadata, no auto-snapshot, no
  on_dlq mapping)

**Risk:** the on_dlq mapper returning `Out: Fact` ties the mapper
type to one Fact enum. Production code's `PipelineEvent::HandlerFailed`
case fits naturally; less common cases may need an `Events`-typed
mapper return. If needed, generalize to `-> Option<Events>` later.

**Estimated effort:** 1 day.

## P12 — Rootsignal migration

**Scope:** Apply the file-by-file migration from the design plan's
table. Done in a single rootsignal PR.

**Files in rootsignal-scout:**
- All `domains/*/events.rs` — Fact impls updated to v0.4 shape
- `core/aggregate.rs` — PipelineState becomes `Aggregate` + many
  `Apply<F>` impls. The `#[aggregators]` macro generates them.
- `domains/curiosity/aggregates.rs` — SignalLifecycle and
  ConcernLifecycle similarly
- All `*_materializer.rs` × 5 — rename to `*_projector.rs`,
  Materializer → Projector, materialize → project, add GROUP_NAME
- All `*_reactor.rs` × 8 — add GROUP_NAME
- `core/v03_engine.rs` — drop second-string-arg on registrations,
  add `with_aggregators` / `with_projectors` calls
- `core/engine.rs` — delete entirely (legacy engine path)
- All `ctx.aggregate` / `aggregate_of` call sites — unchanged
- All `engine.emit` test sites — unchanged
- All `engine.append::<A>` call sites — none exist currently

**Domain restructure (the bigger lift):**

SchedulingEvent → ScheduleEvent + ScrapeScheduleEvent split:
- One Fact enum cannot span two stream categories under v0.4
- The variants must split into two enums
- The materializers that consumed both update accordingly

LifecycleEvent + ScrapeEvent → realigned categories:
- Today both target scout_run streams
- Under v0.4 each Fact enum has its own category
- Streams change layout: `lifecycle-{run_id}` and `scrape-{run_id}`
  separately, rather than both targeting `scout_run-{run_id}`
- Migration script needed to move events from old scout_run streams
  to new category-scoped streams (pre-launch, so easier than post-)

**Acceptance criteria:**
- `cargo build -p rootsignal-scout` succeeds against causal 0.4
- All rootsignal-scout tests pass
- All v03 integration tests pass
- No references to removed causal APIs remain

**Risk:** the stream-layout refactor (LifecycleEvent + ScrapeEvent
each getting their own category) requires reorganizing how
PipelineState is hydrated. Today it folds from one logical stream
(scout_run); after, it folds from N logical streams. The engine
already supports multi-stream folds via Apply<F> dispatch on
event_type — so the registration is unchanged, but the test
fixtures that emit events to scout_run streams need to emit to the
new category-scoped streams instead.

**Estimated effort:** 5-7 days (was 3-5; expanded to include P0
migration runbook execution + verification of stream layout
changes).
