# v0.4 trade-off deep dive — show, don't tell

## Why this document

The audit identified three showstoppers and four engine-feature gaps,
each with options A/B and a recommendation. That left the
recommendations as "trust me" calls. This document **shows the code
under each option** — side-by-side comparisons of real production
files, call sites, and subscription mechanics — so the decisions can
be made on visible evidence rather than my framing.

## S1 in concrete code — Aggregate vs View

### Production code (PipelineState today)

`rootsignal-scout/src/core/aggregate.rs:553-608`:

```rust
impl Aggregate for PipelineState {
    fn aggregate_type() -> &'static str { "ScoutRun" }
}

#[aggregators(singleton)]
pub mod pipeline_aggregators {
    fn on_signal(state: &mut PipelineState, event: SignalEvent)         { state.apply_signal(&event); }
    fn on_scrape(state: &mut PipelineState, event: ScrapeEvent)         { state.apply_scrape(&event); }
    fn on_discovery(state: &mut PipelineState, event: DiscoveryEvent)   { state.apply_discovery(&event); }
    fn on_pipeline(state: &mut PipelineState, event: PipelineEvent)     { state.apply_pipeline(&event); }
    fn on_synthesis(state: &mut PipelineState, event: SynthesisEvent)   { state.apply_synthesis(&event); }
    fn on_enrichment(state: &mut PipelineState, event: EnrichmentEvent) { state.apply_enrichment(&event); }
    fn on_expansion(state: &mut PipelineState, event: ExpansionEvent)   { state.apply_expansion(&event); }
    fn on_lifecycle(state: &mut PipelineState, event: LifecycleEvent)   { state.apply_lifecycle(&event); }
    fn on_world(state: &mut PipelineState, event: WorldEvent)           { state.apply_world(&event); }
```

Used like this in reactor bodies (~20 sites, e.g. `discovery/mod.rs:32`):

```rust
let state = ctx.aggregate::<PipelineState>().curr;
if state.has_tension_web_sources() { /* ... */ }
```

**What's actually happening:** in-memory state is folded from 13 event
streams as they flow past. Reactors read it to make decisions. Nothing
ever calls `engine.append::<PipelineState>(...)` — there's no write-
side OCC contract being exercised.

### Option A in code — multi-Fact Aggregate via `Apply<F>`

Causal exposes:

```rust
pub trait Aggregate: Default + Send + Sync + 'static {
    const NAME: &'static str;
}

pub trait Apply<F: Fact>: Aggregate {
    fn apply(&mut self, fact: &F);
}
```

Rootsignal stays roughly as-is, just translates the macro output:

```rust
impl Aggregate for PipelineState {
    const NAME: &'static str = "ScoutRun";
}

impl Apply<SignalEvent>          for PipelineState { fn apply(&mut self, e: &SignalEvent) { self.apply_signal(e); } }
impl Apply<ScrapeEvent>          for PipelineState { fn apply(&mut self, e: &ScrapeEvent) { self.apply_scrape(e); } }
impl Apply<DiscoveryEvent>       for PipelineState { fn apply(&mut self, e: &DiscoveryEvent) { self.apply_discovery(e); } }
// ... 10 more
```

Or via macro:

```rust
#[aggregator(singleton, name = "ScoutRun")]
impl PipelineState {
    fn apply(&mut self, e: &SignalEvent)         { self.apply_signal(e); }
    fn apply(&mut self, e: &ScrapeEvent)         { self.apply_scrape(e); }
    // ... 10 more — macro generates Aggregate + Apply<F> impls
}
```

Reactor call sites unchanged:

```rust
let state = ctx.aggregate::<PipelineState>().curr;
```

**Cost on causal:** Aggregate trait has no `type Fact` — it's a
naked marker trait with `Apply<F>` extensions. The engine's
`load::<A>(id)` either doesn't work for these (since there's no
canonical Fact type) or requires extra wiring.

**Cost on a TRUE write-side aggregate (hypothetical Schedule with CAS):**

```rust
impl Aggregate for Schedule {
    const NAME: &'static str = "Schedule";
}
impl Apply<ScheduleEvent> for Schedule {
    fn apply(&mut self, e: &ScheduleEvent) { /* ... */ }
}

// Command handler:
let (schedule, version) = engine.load::<Schedule>(id).await?;
// ^ but which Fact type does engine.load fold? Aggregate has no
//   `type Fact` — engine has to look up which Apply<F> impl exists.
//   For an aggregate with ONE Apply, this works. For PipelineState
//   with 13, load is ambiguous (it can't return a coherent state
//   from a single stream).
engine.emit(ScheduleEvent::Triggered { /* ... */ }).expecting(version).await?;
```

So `engine.load` would need to figure out which Fact type to fold —
not impossible (look up Apply impls for the aggregate type, find one
matching the target stream's event types), but requires runtime
trait introspection.

**Observed feel:** muddier. The trait does double duty (write-side
single-Fact AND read-side multi-Fact); the runtime has to disambiguate.
Production won't feel the muddiness because production is all read-side
multi-Fact. But the trait surface lies about its real shape.

### Option B in code — Aggregate (write) + View (read) split

Causal exposes:

```rust
// Write-side. Single Fact. CAS-protected. Owns a stream category.
pub trait Aggregate: Default + Send + Sync + 'static {
    type Fact: Fact;
    fn apply(&mut self, fact: &Self::Fact);
}

// Read-side. Multi-Fact via Apply. In-memory fold. No stream identity.
pub trait View: Default + Send + Sync + 'static {
    const NAME: &'static str;
}

pub trait ApplyTo<F: Fact>: View {
    fn apply(&mut self, fact: &F);
}
```

Rootsignal `PipelineState` becomes a View:

```rust
impl View for PipelineState {
    const NAME: &'static str = "ScoutRun";
}

impl ApplyTo<SignalEvent>    for PipelineState { fn apply(&mut self, e: &SignalEvent)    { self.apply_signal(e); } }
impl ApplyTo<ScrapeEvent>    for PipelineState { fn apply(&mut self, e: &ScrapeEvent)    { self.apply_scrape(e); } }
// ... 10 more
```

Or via macro:

```rust
#[view(singleton, name = "ScoutRun")]
impl PipelineState {
    fn apply(&mut self, e: &SignalEvent)    { self.apply_signal(e); }
    fn apply(&mut self, e: &ScrapeEvent)    { self.apply_scrape(e); }
    // ...
}
```

Reactor call sites rename:

```rust
// Before:
let state = ctx.aggregate::<PipelineState>().curr;

// After:
let state = ctx.view::<PipelineState>().curr;
```

Twenty call sites in rootsignal. Mechanical sed.

Rootsignal's curiosity aggregates (single-Fact, also never CAS-written):

```rust
// Before:
impl Aggregate for SignalLifecycle {
    fn aggregate_type() -> &'static str { "SignalLifecycle" }
}
#[aggregators]
pub mod curiosity_aggregators {
    #[aggregator(id_fn = "lifecycle_signal_id")]
    fn on_signal_lifecycle(state: &mut SignalLifecycle, event: CuriosityEvent) { /* ... */ }
}

// After (View — they're read-side):
impl View for SignalLifecycle {
    const NAME: &'static str = "SignalLifecycle";
}
impl ApplyTo<CuriosityEvent> for SignalLifecycle {
    fn apply(&mut self, e: &CuriosityEvent) { /* ... */ }
}
```

A TRUE write-side aggregate, if rootsignal ever adds one:

```rust
impl Aggregate for Schedule {
    type Fact = ScheduleEvent;
    fn apply(&mut self, fact: &ScheduleEvent) { /* ... */ }
}

// Command handler — engine.load knows exactly which Fact to fold:
let (schedule, version) = engine.load::<Schedule>(id).await?;
engine.emit(ScheduleEvent::Triggered { /* ... */ })
    .expecting(version)
    .await?;
```

`engine.load::<Schedule>(id)` is unambiguous: read the stream
`schedule-{id}`, fold all `ScheduleEvent` facts via the single
`apply` method, return state + version.

**Observed feel:** each trait does one job. Aggregate is the strict
write-side primitive; View is the loose read-side fold. Production
uses View; future write-side commanders use Aggregate. The API
surface tells the truth.

### Side-by-side trade-off

| Aspect | Option A (multi-Fact Aggregate) | Option B (Aggregate + View split) |
|---|---|---|
| Trait count | 2 (Aggregate, Apply<F>) | 4 (Aggregate, View, ApplyTo<F>, plus apply on Aggregate) |
| `engine.load::<A>(id)` shape | Ambiguous — must look up Apply impls | Unambiguous — uses `A::Fact` |
| `engine.emit(fact).expecting(v)` valid for | Any Aggregate impl (even multi-Fact PipelineState — incorrect but compiles) | Only single-Fact Aggregates by construction |
| `ctx` accessor | `ctx.aggregate::<X>()` | `ctx.view::<X>()` (new) + `ctx.aggregate::<A>()` (kept, for write-side) |
| Maps to Kurrent | Awkward — Kurrent aggregates are single-stream-scope; multi-Fact muddies that | Direct — Aggregate maps to Kurrent stream; View has no Kurrent equivalent (in-process abstraction) |
| Macro complexity | One macro generates everything | Two macros (`#[aggregator]`, `#[view]`) but each simpler |
| Rootsignal migration LOC | ~30 lines (translate macro output) | ~30 lines + ~25 `ctx.aggregate` → `ctx.view` renames |
| Documentation burden | "Aggregate sometimes is read-side multi-Fact, sometimes write-side single-Fact" | "Aggregate is write-side; View is read-side" |
| Future write-side ergonomics | Awkward — same trait, different semantics by impl shape | Clean — Aggregate has the constraints write-side needs |

**My recommendation stays Option B.** The split makes the semantic
difference visible. Option A's "one trait with two faces" is a tax
paid on every new consumer learning the API.

### What about the singleton vs keyed distinction?

Independent of Aggregate-vs-View. Both options support singleton via a
nil id or a `#[singleton]` macro tag. The `ctx.aggregate()` /
`ctx.aggregate_of(id)` split (D7) stays under both options — just
becomes `view()` / `view_of(id)` for views under Option B.

## S2 in concrete code — one-axis vs two-axis Fact model

### Production data (exhaustive Fact survey)

I'll show all 5 prefix-declaring Fact enums in rootsignal:

```rust
// scheduling/events.rs
#[causal::event(prefix = "scheduling")]
pub enum SchedulingEvent {
    ScheduleCreated { schedule_id: String, /* ... */ },        // → category="schedule"
    ScheduleToggled { schedule_id: String, /* ... */ },        // → category="schedule"
    ScheduleTriggered { schedule_id: String, /* ... */ },      // → category="schedule"
    ScheduleDeleted { schedule_id: String, /* ... */ },        // → category="schedule"
    ScheduleCadenceAdjusted { schedule_id: String, /* ... */ },// → category="schedule"
    ScrapeScheduled { scope: ScheduledScope, /* ... */ },      // → category="scrape_schedule"
}

// discovery/events.rs
#[causal::event(prefix = "discovery")]
pub enum DiscoveryEvent { /* ... */ }
// all variants: → category="discovery"  (prefix == category, aligned)

// lifecycle/events.rs
#[causal::event(prefix = "lifecycle")]
pub enum LifecycleEvent {
    PhaseCompleted { run_id, phase, .. },        // → category="scout_run"
    ScoutRunCompleted { run_id, .. },            // → category="scout_run"
    /* ... */
}

// scrape/events.rs
#[causal::event(prefix = "scrape")]
pub enum ScrapeEvent {
    SourceScraped { run_id, .. },     // → category="scout_run"
    /* ... */
}

// telemetry_events.rs
#[causal_core_macros::event(prefix = "telemetry")]
pub enum TelemetryEvent { /* ... */ }
// all variants: → category="telemetry"  (prefix == category, aligned)
```

Three patterns visible:
1. **Aligned** (DiscoveryEvent, TelemetryEvent): prefix == category. Single source of truth.
2. **One-Fact, multi-category** (SchedulingEvent): one enum, two categories.
3. **Multi-Fact, one-category** (Lifecycle + Scrape → scout_run): two enums target the same stream.

### What "one-axis" forces (S2 Option B)

Forcing `Fact::CATEGORY` as a const means pattern 2 is illegal — every
variant of a Fact enum must share one category.

**SchedulingEvent must split:**

```rust
// Before: one enum, two categories (illegal under one-axis).
#[causal::event(prefix = "scheduling")]
pub enum SchedulingEvent {
    ScheduleCreated { schedule_id: String, .. },
    /* ... 4 more variants on category=schedule ... */
    ScrapeScheduled { scope: ScheduledScope, .. },  // category=scrape_schedule
}

// After: two enums, each one category.
impl Fact for ScheduleEvent {
    const CATEGORY: &'static str = "schedule";
    /* variants: Created/Toggled/Triggered/Deleted/CadenceAdjusted */
}

impl Fact for ScrapeScheduleEvent {
    const CATEGORY: &'static str = "scrape_schedule";
    /* variants: ScrapeScheduled */
}
```

**LifecycleEvent + ScrapeEvent (pattern 3) get harder.** They both
target `scout_run` streams today — different bounded contexts writing
events about the same entity. Under one-axis:

```rust
// Option B1: each Fact gets its own category. Streams split.
impl Fact for LifecycleEvent {
    const CATEGORY: &'static str = "lifecycle";  // streams: "lifecycle-{run_id}"
}
impl Fact for ScrapeEvent {
    const CATEGORY: &'static str = "scrape";     // streams: "scrape-{run_id}"
}
// Cross-domain "scout run state" becomes a Projector that subscribes
// to both categories. PipelineState (the View) builds itself by
// folding events from BOTH streams.

// Option B2: unify into one giant enum.
impl Fact for ScoutRunEvent {
    const CATEGORY: &'static str = "scout_run";
    // ScoutRunEvent has variants from Lifecycle + Scrape + 11 more domains
}
// 13 domains' worth of facts in one enum. Hostile to domain boundaries.
```

B1 is cleaner. But it splits what's currently one stream into 13 streams
per run. Reading the "history of run X" requires merging 13 streams. In
Kurrent, this is `$ce-lifecycle` + `$ce-scrape` + 11 more, merged by
commit position — works but not as clean as a single `scout_run-{id}`
stream.

### What "two-axis" looks like (S2 Option A)

Keep both:

```rust
pub trait Fact {
    /// Subscription axis. Projectors subscribe by this.
    const NAMESPACE: &'static str;

    /// Event name within the namespace.
    fn name(&self) -> &str;

    /// Per-variant storage. Can differ between variants of one enum.
    fn stream(&self) -> StreamRef;
}

pub struct StreamRef {
    pub category: &'static str,
    pub id: Uuid,
}
```

Production stays exactly as it is today, just with renames:

```rust
impl Fact for SchedulingEvent {
    const NAMESPACE: &'static str = "scheduling";
    fn name(&self) -> &str {
        match self {
            Self::ScheduleCreated { .. } => "schedule_created",
            Self::ScrapeScheduled { .. } => "scrape_scheduled",
            /* ... */
        }
    }
    fn stream(&self) -> StreamRef {
        match self {
            Self::ScheduleCreated { schedule_id, .. } /* ... */ =>
                StreamRef { category: "schedule", id: uuid_from_str(schedule_id) },
            Self::ScrapeScheduled { scope, .. } =>
                StreamRef { category: "scrape_schedule", id: scope_id(scope) },
        }
    }
}
```

Pattern 2 (SchedulingEvent) still legal. Pattern 3 (Lifecycle +
Scrape both targeting scout_run) still legal.

### Subscription mechanics — what actually happens in the backend

This is where it matters. Let me trace what a Projector subscription
runs as SQL against the Postgres backend.

**One-axis, B1 (separate categories):**

```rust
// In rootsignal:
impl Projector for ScoutRunProjector {
    type Fact = LifecycleEvent;
    const GROUP_NAME: &'static str = "scout_run";
    /* ... */
}
```

Backend query (Postgres EventLog):
```sql
SELECT * FROM events
WHERE position > $cursor
  AND aggregate_type = 'lifecycle'  -- LifecycleEvent::CATEGORY
ORDER BY position
LIMIT $batch;
```

But ScoutRunProjector wants to see Scrape events too. So it has to be
a MultiProjector:
```rust
impl MultiProjector for ScoutRunProjector {
    const CATEGORIES: &'static [&'static str] = &["lifecycle", "scrape"];
    const GROUP_NAME: &'static str = "scout_run";
    /* takes &PersistedEvent — raw, dispatches by event_type internally */
}
```

Backend query:
```sql
SELECT * FROM events
WHERE position > $cursor
  AND aggregate_type IN ('lifecycle', 'scrape', 'pipeline', 'synthesis', /* 9 more */)
ORDER BY position
LIMIT $batch;
```

13 categories joined for what was conceptually one entity. Workable
but the consumer is now `MultiProjector`, taking raw `&PersistedEvent`
and dispatching internally — losing the typed-Fact ergonomics.

**Two-axis (current shape):**

```rust
impl Projector for ScoutRunProjector {
    type Fact = LifecycleEvent;  // or ScrapeEvent, etc.
    const GROUP_NAME: &'static str = "scout_run";
}
```

Backend query (subscribes by NAMESPACE):
```sql
SELECT * FROM events
WHERE position > $cursor
  AND event_type LIKE 'lifecycle:%'
ORDER BY position
LIMIT $batch;
```

For cross-domain, MultiProjector with namespaces (not categories):
```rust
impl MultiProjector for ScoutRunProjector {
    const NAMESPACES: &'static [&'static str] = &["lifecycle", "scrape", /* ... */];
    const GROUP_NAME: &'static str = "scout_run";
}
```

```sql
SELECT * FROM events
WHERE position > $cursor
  AND (event_type LIKE 'lifecycle:%' OR event_type LIKE 'scrape:%' OR ...)
ORDER BY position
LIMIT $batch;
```

**The plumbing is symmetric.** Both axes translate to SQL `WHERE`
clauses on different columns. Both fit Kurrent's $all-with-filter.

### Where each model breaks down

**One-axis breaks when:**
- An entity legitimately has events from multiple bounded contexts
  (the scout_run case). Forcing them apart loses stream identity.
- A bounded context legitimately spans multiple entity types (the
  scheduling case). Splitting the enum is mechanical but creates
  artificial domain boundaries.

**Two-axis breaks when:**
- Consumers confuse the axes ("is this NAMESPACE or CATEGORY?"). The
  current code's `type_prefix` vs `category` naming made this worse;
  v0.4 naming (NAMESPACE vs CATEGORY) is sharper but still requires
  doc work.
- Subscription efficiency: `event_type LIKE 'X:%'` may be slower than
  `aggregate_type = 'X'` if the backend's index is on aggregate_type
  not event_type. Mitigation: index event_type too.

### Side-by-side trade-off

| Aspect | Option A (two-axis) | Option B (one-axis) |
|---|---|---|
| Fact trait surface | `NAMESPACE` const + `name()` + `stream()` returning `StreamRef` | `CATEGORY` const + `name()` + `stream_id()` returning `Uuid` |
| Rootsignal migration | Mechanical rename of `type_prefix` → `NAMESPACE`, `type_name` → `name` (returning bare variant) | SchedulingEvent split + scout_run streams split into 13 categories + cross-domain consumers become MultiProjector |
| Cross-domain entity (scout_run) | Stays one stream, multiple Fact enums write to it | Stream splits into N streams; cross-domain reads via MultiProjector merging |
| Kurrent backend implementation | $all subscription with event_type prefix filter | $ce-{category} subscription (more native) |
| Typed Projector ergonomics for cross-domain views | Native (single typed Fact even for cross-cutting) | Forced to MultiProjector with raw `&PersistedEvent` |
| Conceptual sharpness | Two axes — subscription vs storage — explicitly named | One axis — but loses the "different domains, same entity" expressivity |

**My recommendation stays Option A (two-axis).** The cross-domain
entity case (scout_run with both Lifecycle and Scrape facts) is a
legitimate event-sourcing pattern, and forcing it into MultiProjector
loses the typed Fact ergonomics. The cost — two axes to name and
document — is real but bounded.

**Rootsignal still refactors SchedulingEvent** (the only pattern-2
violation) — splits into ScheduleEvent + ScrapeScheduleEvent so each
Fact enum maps to one category. Best of both: expressive two-axis
model + per-Fact storage hygiene.

## Engine features (G1, G2, G3) — what they actually do

### G1 — on_dlq, in flow

**Today's flow:**

```rust
// rootsignal-scout/src/core/engine.rs:142-147
let mut engine = causal::Engine::new(deps)
    .on_dlq(|info: causal::DlqTerminalInfo| PipelineEvent::HandlerFailed {
        handler_id: info.reactor_id.clone(),
        source_event_type: info.source_event_type.clone(),
        error: info.error.clone(),
        attempts: info.attempts,
    });
```

When a reactor exhausts retries, the engine calls the mapper with
metadata about the failure. The returned Fact gets emitted into the
log. Downstream reactors (e.g., a "send alert to ops" reactor) can
subscribe to `HandlerFailed` and respond.

**Why this earns its weight:** without it, retry-exhausted failures
disappear into log lines. With it, they're first-class facts that the
causal chain can react to. A common pattern: "if any handler in this
run failed, emit a RunFailed event."

**Proposed v0.4 shape:**

```rust
pub struct DlqInfo {
    pub group_name: String,           // matches the trait's GROUP_NAME
    pub source_event_id: Uuid,
    pub source_event_type: String,
    pub error: String,
    pub attempts: u32,
}

impl EngineBuilder {
    pub fn on_dlq<F, Out>(self, mapper: F) -> Self
    where
        F: Fn(DlqInfo) -> Option<Out> + Send + Sync + 'static,
        Out: Fact;
}
```

Returning `Option<Out>` lets the mapper choose not to emit (e.g.,
"only emit for certain handlers"). Stays out of the runtime if not
configured.

### G2 — metadata, two layers

**Today's flow:** rootsignal stamps `run_id` + `schema_v` on every
event via `engine.with_event_metadata(...)`. The metadata travels in
each event's `metadata` field; consumers read `ctx.metadata.get("run_id")`
to scope by run.

```rust
engine = engine.with_event_metadata(serde_json::json!({
    "run_id": run_id,
    "schema_v": 1,
}));
```

**Why this earns its weight:** without it, every `engine.emit(...)`
call would have to pass `run_id` explicitly. With 100+ emit sites,
that's repetitive and error-prone.

**Proposed v0.4 shape — two layers:**

```rust
// Engine-level default (stamped on every emit):
EngineBuilder::new(/* ... */)
    .with_default_metadata(serde_json::json!({
        "run_id": run_id,
        "schema_v": 1,
    }))
    .build();

// Per-emit override (merges over the default):
engine.emit(fact)
    .metadata("override_key", value)
    .await?;
```

Per-emit metadata merges over defaults: if both define `run_id`,
per-emit wins. Per-emit is rarely needed (most metadata is run-scope
defaults).

Note: I previously argued against `.metadata` on the EmitBuilder
because reactors don't call emit. Tests do; boundary code does. They
sometimes need per-emit metadata. Adding it back.

### G3 — snapshot_every, why and what

**Today's flow:**

```rust
engine.snapshot_every(100)
```

After every 100 events applied to an aggregate, the engine calls
`SnapshotStore::save` to persist the aggregate's serialized state.
Next time the aggregate is hydrated (e.g., on engine restart),
hydration loads the latest snapshot and replays only the events past
the snapshot version — bounded replay regardless of stream length.

Without snapshots, a stream of 10,000 events forces 10,000 fold
operations on every hydration. With snapshots every 100, hydration
loads snapshot at v9900 and folds 100 events.

**Why this earns its weight:** unbounded stream length is the
catastrophic-failure mode of event sourcing without snapshots. For
long-running entities (a scout_run that produces 1000+ events),
hydration latency dominates.

**Proposed v0.4 shape:**

```rust
EngineBuilder::new(/* ... */)
    .snapshot_every(100)  // per-aggregate event count threshold
    .build();
```

Same as today. Engine's settle loop calls `SnapshotStore::save` when
any aggregate's `apply` count since last snapshot exceeds the
threshold. Backends without snapshots (no-op `SnapshotStore` impl)
ignore.

Under S1 Option B (Aggregate vs View split), snapshots apply to
**Aggregates only** — Views are in-memory and don't persist, so they
don't snapshot. This is a clean simplification: snapshot semantics
match the write-side OCC-protected entity, not the multi-Fact read
fold.
