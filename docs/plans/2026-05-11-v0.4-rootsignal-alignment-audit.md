# v0.4 plan vs rootsignal — alignment audit

## Overview

After committing the v0.4 plan as "design-locked," I audited it against
rootsignal-scout (the production consumer) and found significant gaps.
Rootsignal hasn't launched, so we have two options for each gap:
**causal accommodates** (extend the v0.4 surface) or **rootsignal
refactors** (change rootsignal to fit the simpler shape).

This document lists every gap with evidence from the rootsignal code,
proposes both options, and recommends one based on what produces the
sharpest library AND a clean consumer. Since rootsignal is pre-launch,
"clean consumer" can outweigh "minimal migration cost."

Net result: the plan needs revision on three decisions (D2, D3, D5)
plus four engine-feature additions. About half the plan stands; the
other half needs the corrections below before it's actually locked.

## Method

For each of the v0.4 plan's nine design decisions, I checked:
- Every `impl Fact for X` in rootsignal (~12 files)
- Every `impl Aggregate for X` (3 aggregates, plus the legacy
  `Apply<E>`-via-macro form in `core/aggregate.rs:559-608`)
- All `with_aggregators`, `with_reactor`, `with_projector`-style
  registration call sites
- All `engine.emit`, `engine.append`, `engine.emit_in` call sites
- All `ctx.aggregate*` access patterns
- Legacy engine features used in `core/engine.rs:129-179`

## Showstoppers

These break the v0.4 plan as written. Each needs a decision before
implementation starts.

### S1: Production aggregates fold MANY Fact types; v0.4 forces ONE

**Evidence.** `rootsignal-scout/src/core/aggregate.rs:553-608`:

```rust
impl Aggregate for PipelineState {
    fn aggregate_type() -> &'static str { "ScoutRun" }
}

#[aggregators(singleton)]
pub mod pipeline_aggregators {
    fn on_signal(state: &mut PipelineState, event: SignalEvent)         { /* ... */ }
    fn on_scrape(state: &mut PipelineState, event: ScrapeEvent)         { /* ... */ }
    fn on_discovery(state: &mut PipelineState, event: DiscoveryEvent)   { /* ... */ }
    fn on_pipeline(state: &mut PipelineState, event: PipelineEvent)     { /* ... */ }
    fn on_synthesis(state: &mut PipelineState, event: SynthesisEvent)   { /* ... */ }
    fn on_enrichment(state: &mut PipelineState, event: EnrichmentEvent) { /* ... */ }
    fn on_expansion(state: &mut PipelineState, event: ExpansionEvent)   { /* ... */ }
    fn on_lifecycle(state: &mut PipelineState, event: LifecycleEvent)   { /* ... */ }
    fn on_world(state: &mut PipelineState, event: WorldEvent)           { /* ... */ }
    fn on_system(state: &mut PipelineState, event: SystemEvent)         { /* ... */ }
    fn on_telemetry(_: &mut PipelineState, _: TelemetryEvent)           {}
    fn on_situation_weaving(_: &mut PipelineState, _: SituationWeavingEvent) {}
    fn on_supervisor(_: &mut PipelineState, _: SupervisorEvent)         {}
}
```

`PipelineState` folds **13 different Fact enums**. The v0.4 plan's
`Aggregate { type Fact: Fact; }` can express only one.

**Deeper observation.** `PipelineState` is never CAS-written. No
`engine.append::<PipelineState>(...)` exists anywhere. It's hydrated
from the event stream and read via `ctx.aggregate::<PipelineState>()`
in 20+ reactor bodies. It's a **read-side fold**, not a write-side
consistency boundary.

The v0.3 design conflated two things into `Aggregate`:
- **Write-side OCC anchor** — `engine.load + append::expecting` —
  single Fact, single stream, CAS-protected
- **Read-side derived state** — multi-Fact fold available to reactors

`PipelineState` is the second; `Schedule` would be the first if
anything actually CAS-wrote to it (nothing does in rootsignal — every
write goes through `emit` without `expecting`).

#### Two options

**Option A — Causal accommodates: keep multi-Fact aggregates.**
Bring back the `Apply<F: Fact>` extension trait family. Aggregate
declares the aggregate type; `Apply<F>` impls declare which Facts it
folds. Macro generates the registry.

```rust
pub trait Aggregate: Default + Send + Sync + 'static {
    const NAME: &'static str;
}

pub trait Apply<F: Fact>: Aggregate {
    fn apply(&mut self, fact: &F);
}

impl Aggregate for PipelineState { const NAME: &'static str = "ScoutRun"; }
impl Apply<SignalEvent>    for PipelineState { fn apply(&mut self, e: &SignalEvent) { /* ... */ } }
impl Apply<ScrapeEvent>    for PipelineState { fn apply(&mut self, e: &ScrapeEvent) { /* ... */ } }
// ... 11 more
```

**Cost:** ~15 trait impls per cross-domain aggregate. Macro absorbs it.
Loses the "Aggregate IS the OCC anchor" invariant — pure write-side
aggregates and pure read-side aggregates use the same trait, only
the `Apply<F>` set varies.

**Option B — Rootsignal refactors: split Aggregate (write) vs View (read).**

```rust
// Write-side. Single Fact. CAS-protected. Owns a stream category.
// engine.load<A>(id) hydrates. emit.expecting(v) CAS-writes.
pub trait Aggregate: Default + Send + Sync + 'static {
    type Fact: Fact;
    const CATEGORY: &'static str;
    fn apply(&mut self, fact: &Self::Fact);
}

// Read-side. Multi-Fact via Apply<F>. In-memory fold, no CAS,
// no stream identity. Accessed via ctx.view::<V>() in reactor bodies.
pub trait View: Default + Send + Sync + 'static {
    const NAME: &'static str;
}

pub trait ApplyTo<F: Fact>: View {
    fn apply(&mut self, fact: &F);
}
```

Rootsignal migration:
- `PipelineState` becomes a `View` (it's never CAS-written; it's a
  multi-Fact read-side fold)
- `SignalLifecycle`, `ConcernLifecycle` become `View`s (single-Fact
  but read-only — never CAS-written, accessed via `ctx.view_of(id)`)
- If/when rootsignal needs a CAS-protected entity (e.g., a true
  Schedule write model), it implements `Aggregate` instead

In `ctx`: `ctx.view::<V>()` replaces `ctx.aggregate::<A>()` for these.
`ctx.aggregate::<A>(id)` stays for actual write-side aggregates.

**Cost:** rootsignal renames ~3 trait impls (PipelineState,
SignalLifecycle, ConcernLifecycle) plus all ~25 `ctx.aggregate` call
sites become `ctx.view`. Plus the macro split — `#[views]` vs
`#[aggregators]`.

**Recommendation: Option B.**

Reasons:
1. **It's the conceptually correct split.** Production already shows
   the two concerns are different — nothing in rootsignal uses the
   write-side facet of `Aggregate` (no CAS writes). The trait was
   doing two jobs; production used only one. Making the split explicit
   in the API surfaces the semantic difference.
2. **Single-Fact `Aggregate` matches Kurrent's aggregate model
   cleanly.** Kurrent aggregates are stream-scoped + CAS-protected.
   `View` has no Kurrent equivalent because it's an in-process
   abstraction — but it doesn't conflict with anything either.
3. **Migration cost is bounded** — ~3 trait impl rewrites + a
   global rename of `ctx.aggregate` → `ctx.view` for the read-side
   case. Mechanical.
4. **Future write-side aggregates get the strict shape they need**
   without ambiguity. If rootsignal ever wants a real CAS-protected
   `Schedule` write model, it implements `Aggregate` and the OCC
   semantics work end-to-end.

The v0.4 plan's D3 (Aggregate inherits CATEGORY from Fact) holds
under Option B — the single-Fact Aggregate trait inherits cleanly.

### S2: NAMESPACE (subscription) vs CATEGORY (storage) genuinely diverge

**Evidence.** Surveyed every `impl Fact for X` in rootsignal:

| Fact enum | `type_prefix` | stream `category` |
|---|---|---|
| `SchedulingEvent` | `"scheduling"` | `"schedule"` AND `"scrape_schedule"` |
| `DiscoveryEvent` | `"discovery"` | `"discovery"` |
| `LifecycleEvent` | `"lifecycle"` | `"scout_run"` |
| `ScrapeEvent` | `"scrape"` | `"scout_run"` |
| `TelemetryEvent` | `"telemetry"` | `"telemetry"` |

Two patterns the v0.4 plan can't express:
- **One Fact enum, multiple stream categories** (SchedulingEvent has
  variants in two different stream categories — recurring schedule
  events vs one-shot scrape-schedule events)
- **Multiple Fact enums, same stream category** (LifecycleEvent +
  ScrapeEvent both write to `scout_run-{id}` streams — different
  bounded contexts observing the same entity)

The current `type_prefix` (subscription axis) and `stream().category`
(storage axis) are **orthogonal**. Plan's D2 collapsed them to one
axis — wrong.

#### Two options

**Option A — Causal accommodates: reinstate two-axis model.**

```rust
pub trait Fact: Serialize + DeserializeOwned + Send + Sync + 'static {
    /// Subscription axis. Projectors subscribe by this.
    const NAMESPACE: &'static str;

    /// Per-variant event name within the namespace. Stored as
    /// `event_type = "{NAMESPACE}:{name()}"`.
    fn name(&self) -> &str;

    /// Per-variant storage axis. Different variants of one Fact enum
    /// can target different stream categories.
    fn stream(&self) -> StreamRef;
}

pub struct StreamRef {
    pub category: &'static str,
    pub id: Uuid,
}
```

Subscriptions: `Projector<Fact = F>` subscribes to events where
`event_type` starts with `{F::NAMESPACE}:`. Kurrent equivalent:
`$all` with prefix filter on event_type. Slightly less efficient than
`$ce-{category}` but supported natively.

**Cost on rootsignal:** zero — this matches today's shape exactly.

**Option B — Rootsignal refactors: align axes (one Fact = one category).**

Force `Fact::CATEGORY` as a const; subscription IS by stream category.
Rootsignal splits enums and reorganizes streams:

```rust
// SchedulingEvent currently spans two categories — split:
enum ScheduleEvent { ScheduleCreated, ScheduleTriggered, ScheduleDeleted, /* ... */ }
impl Fact for ScheduleEvent { const CATEGORY: &'static str = "schedule"; }

enum ScrapeScheduleEvent { ScrapeScheduled }
impl Fact for ScrapeScheduleEvent { const CATEGORY: &'static str = "scrape_schedule"; }

// LifecycleEvent + ScrapeEvent both target scout_run — choose:
// Option B1: separate categories (each Fact gets its own)
//            -> Lifecycle and Scrape get distinct stream categories;
//               cross-domain "scout run state" is a Projector, not a stream
// Option B2: unify into one Fact enum
//            -> One ScoutRunEvent enum across all 13 domains (huge,
//               cross-cuts boundaries, probably wrong)
```

B1 is the clean version. Each bounded context owns its own stream
category; cross-domain views are projector-driven, not write-side
co-stream.

**Cost on rootsignal:** ~5-10 new Fact enums (splitting existing
ones), ~3-5 stream category renames, all Projectors that span
domains become MultiProjectors (already exists in plan). Migration
script for existing events (rare since not launched).

**Recommendation: Option A.**

This is the only place I'm recommending the "causal accommodates"
path over the rootsignal refactor. Reasons:

1. **The two-axis model is genuinely more expressive** and the
   expressiveness is used productively in rootsignal. Multiple bounded
   contexts observing the same entity (LifecycleEvent + ScrapeEvent on
   `scout_run` streams) is a legitimate event-sourcing pattern —
   different domains contributing facts about the same aggregate.
   Forcing them apart loses information that's worth keeping.
2. **Kurrent supports both axes natively** via `$ce-{category}` and
   event-type filters on `$all`. We're not departing from Kurrent —
   we're using both of its subscription primitives.
3. **The "one Fact enum, multiple categories" case is rarer** and
   could be fixed in rootsignal (SchedulingEvent split) without
   collapsing the broader two-axis design. Refactoring it gets a
   cleaner rootsignal without forcing the constraint on every Fact.
4. **Forces good naming.** When `NAMESPACE` is the subscription
   axis and `category` is the storage axis, naming them well
   resolves the confusion: they're not "two names for the same
   thing" — they're two different things.

Migration recommendation for rootsignal: keep the two-axis model,
but **refactor SchedulingEvent** (the one Fact enum with two
categories) into two enums (`ScheduleEvent` for the schedule entity,
`ScrapeScheduleEvent` for the scrape-schedule entity). Each Fact
enum then targets one category, even though the model permits more.

This gets us the expressive two-axis model AND clean per-Fact
storage hygiene.

### S3: `with_reactors` (bulk) is heavily used; plan only has singular

**Evidence.** `rootsignal-scout/src/core/engine.rs:133-140`:

```rust
.with_reactors(signals::reactors::reactors())
.with_reactors(lifecycle::reactors::reactors())
.with_reactors(scrape::reactors::reactors())
.with_reactors(discovery::reactors::reactors())
.with_reactors(enrichment::reactors::reactors())
.with_reactors(expansion::reactors::reactors())
.with_reactors(synthesis::reactors::reactors())
.with_reactors(curiosity::reactors::reactors())
```

The `#[reactors]` macro generates `pub fn reactors() -> Vec<Reactor>`
per domain. Builder consumes via `with_reactors(I)`. v0.4 plan only
has `with_reactor` (singular) — would force one line per reactor,
turning 8 lines into 50+.

#### Decision

Trivial addition. Add `with_reactors(I)` matching the existing
`with_aggregators(I)` pattern. No design tension.

```rust
impl EngineBuilder {
    pub fn with_reactor<R: Reactor + 'static>(self, reactor: R) -> Self;
    pub fn with_reactors<I>(self, reactors: I) -> Self
    where I: IntoIterator<Item = Box<dyn ReactorRegistration>>;
}
```

Same for `with_projectors(I)` and `with_multi_projectors(I)` for
consistency with the bulk-registration macro pattern.

**Adopt without question.**

## Major gaps — engine features the plan ignored

These are legacy engine features rootsignal uses but the v0.4 plan
doesn't address. Each needs a decision: preserve, replace, or drop.

### G1: `on_dlq` — DLQ event mapper

**Evidence.** `rootsignal-scout/src/core/engine.rs:142-147`:

```rust
.on_dlq(|info: causal::DlqTerminalInfo| PipelineEvent::HandlerFailed {
    handler_id: info.reactor_id.clone(),
    source_event_type: info.source_event_type.clone(),
    error: info.error.clone(),
    attempts: info.attempts,
});
```

When a reactor exhausts its retry budget, the engine calls this
mapper to produce a Fact that gets injected into the causal chain.
Lets the application observe its own DLQ as events.

**Decision needed:** in v3, what's the DLQ surface?

Looking at v3: reactors return `Result<Events>`; on `Err`, the
`ReactorRunner` records the failure to `ReactorOutbox` (via
`record_failure` or equivalent). The failure doesn't become a Fact
in the log unless explicitly mapped.

**Recommendation: preserve.** Add `EngineBuilder::on_dlq(mapper)` to
v0.4. The mapper receives `DlqInfo { group_name, source_event_id,
error, attempts }` and returns a Fact (or `None`). Engine emits the
returned Fact through the outbox path when a reactor terminally
fails. Same semantics as today.

### G2: `with_event_metadata` — global metadata stamping

**Evidence.** `rootsignal-scout/src/core/engine.rs:152-156`:

```rust
engine.with_event_metadata(serde_json::json!({
    "run_id": run_id,
    "schema_v": 1
}))
```

Every emit gets `run_id` and `schema_v` stamped into metadata.
Consumers read `ctx.metadata.get("run_id")` to scope by run.

**Decision needed:** v0.4 plan has no global metadata; only
per-emit metadata via `EmitBuilder`.

**Recommendation: preserve.** Two metadata sources:
- Engine-level (default for every emit): `EngineBuilder::with_default_metadata(json)`
- Per-emit (overrides): `EmitBuilder::metadata(key, value)` — but
  **add this back to the plan** (I removed it claiming reactors don't
  emit; but boundary code AND tests DO emit and might want metadata).

The metadata merges: engine defaults first, per-emit overrides on top.

### G3: `snapshot_every(N)` — auto-snapshots

**Evidence.** `engine.rs:156`: `.snapshot_every(100)`.

Auto-snapshots aggregates every N events. v0.3 has `SnapshotStore`
but I didn't check if auto-snapshot is wired into the v3 engine.

**Decision needed:** does v3 have auto-snapshot? If not, do we add it?

**Recommendation: preserve.** Add `EngineBuilder::snapshot_every(N)`
to v0.4. Implementation: the engine's settle loop checks aggregate
version after each fold; if `version % N == 0`, call `SnapshotStore::save`.
Concrete and matches today's semantics.

### G4: `with_store` — backend selector

**Evidence.** `engine.rs:151`: `.with_store(seesaw_store)` swaps in
the seesaw inspector backend.

In v0.4, backends are passed to `EngineBuilder::new(log, checkpoint,
outbox)` as separate args. The `with_store` shorthand for "this one
type implements all three" doesn't exist.

**Decision needed:** does the constructor-with-three-traits pattern
suffice, or do we add `with_store<S: EventLogBackend + CheckpointStore + ReactorOutbox>`?

**Recommendation: drop.** The constructor pattern is more honest —
backends might not satisfy all three traits, and the cast pattern
(`store as Arc<dyn EventLogBackend>` plus another for checkpoint) is
what production code already does in `v03_engine.rs:95-102`. The
`with_store` shorthand was a v0.2-era convenience that v0.3's split
trait surface obsoletes.

Migration: rootsignal already does the cast pattern in the v3 path.
Legacy engine's `with_store` goes away with the legacy engine.

## Minor things the plan got right

These hold up — no changes needed.

- **`engine.append` / `engine.emit_in` deletion is safe.** No
  rootsignal code uses them. (Tests use `engine.emit_output` which
  is a legacy method also being removed.)
- **`ctx.aggregate_of`** is genuinely used (curiosity module:
  `mod.rs:48, 57, 66, 75`). Keeping both `aggregate()` and
  `aggregate_of(id)` (D7) was right. **Under Option B for S1,
  these become `view()` and `view_of(id)`.**
- **All `Reactor` impls already use v3 `reactor_v3::Reactor`.**
  Twenty trait impls. Rename plan migrates cleanly.
- **`engine.emit` is used in tests** (~30 sites in `engine_tests.rs`,
  `chain_tests.rs`, `completion_tests.rs`, etc.). My "boundary-only"
  framing should be "boundary code or test code." Tests legitimately
  emit Facts to drive reactor chains in isolation. Not a real
  correction; just framing.

## Net effect on v0.4

**Trait count:**
- Original v0.4: Fact, Aggregate, Projector, MultiProjector, Reactor
- After audit: Fact, Aggregate, View, ApplyTo<F>, Projector, MultiProjector, Reactor

One trait added (View), one extension trait family added (ApplyTo<F>).

**EngineBuilder method count:**
- Original: new, with_aggregators, with_projector, with_multi_projector, with_reactor, build
- After audit: + with_reactors, with_projectors, with_multi_projectors, with_views (or fold into with_aggregators?), on_dlq, with_default_metadata, snapshot_every

Roughly 6 new methods. Most are bulk variants of existing methods.

**EmitBuilder:**
- `.expecting(version)` (S1 → on Aggregate only)
- `.metadata(key, value)` (re-added per G2)

**Ctx accessors:**
- `aggregate<A>()`, `aggregate_of<A>(id)` — for write-side Aggregates
- `view<V>()`, `view_of<V>(id)` — for read-side Views (new)
- `now()`, `event_id`, `correlation_id`, `metadata` — unchanged

## Rootsignal migration impact

Updated migration table for rootsignal:

| File / pattern | Change |
|---|---|
| `domains/scheduling/events.rs` | **Split into two Fact enums** — `ScheduleEvent` (category=schedule) and `ScrapeScheduleEvent` (category=scrape_schedule). Their NAMESPACEs can match category or stay as "scheduling" — separate decision. |
| Other `domains/*/events.rs` Fact impls | Replace `type_name()` (returns prefixed string) with `name()` (returns variant-only string). Replace `type_prefix()` (method) with `NAMESPACE` const. Keep `stream()` returning `StreamRef`. |
| `core/aggregate.rs` PipelineState | **Rename Aggregate impl to View impl.** Change `#[aggregators(singleton)]` macro to `#[views(singleton)]` (or equivalent). Body unchanged. |
| `domains/curiosity/aggregates.rs` SignalLifecycle, ConcernLifecycle | Same — `Aggregate` → `View` (single-Fact via `ApplyTo<CuriosityEvent>`). |
| All `ctx.aggregate::<PipelineState>()` calls (20+ sites) | → `ctx.view::<PipelineState>()` |
| All `ctx.aggregate_of::<SignalLifecycle>(id)` calls (4 sites) | → `ctx.view_of::<SignalLifecycle>(id)` |
| `core/engine.rs` legacy engine builder | Will be deleted entirely (legacy engine cut). Migrate features to v3: `with_event_metadata` → `with_default_metadata`, `snapshot_every` → preserved, `on_dlq` → preserved, `with_store` → constructor args. |
| `core/v03_engine.rs` builder | Update for new trait names (Projector vs Materializer, etc.), GROUP_NAME moved to trait consts (drop second registration arg), `with_reactors` bulk used where macro returns Vec. |
| All Projector/Reactor impls | Add `const GROUP_NAME` to trait body. Method rename `materialize` → `project` for projectors. |

Net rootsignal LOC touched: probably ~600-800 lines (up from my
original ~200-400 estimate). Still mechanical, bodies unchanged.

## Next steps

1. **Confirm S1 Option B (Aggregate vs View split).** If you accept,
   the trait family is locked. If not, revert to Option A (Apply<F>
   on Aggregate, no View) and the migration is smaller but the
   abstraction is muddier.

2. **Confirm S2 Option A (two-axis Fact model).** Reinstates
   `NAMESPACE` alongside `stream().category`. Plus the rootsignal
   refactor of SchedulingEvent to one-category-per-Fact discipline.

3. **Adopt S3 + G1 + G2 + G3 without further discussion** — they're
   mechanical additions that production needs.

4. **Drop G4** — constructor pattern wins.

5. **Update the v0.4 plan doc** with the corrections from above.
   Mark the plan's status back to `design-locked` once these
   decisions land. (Today it's effectively `design-needs-revision`
   pending these answers.)

6. **Audit other consumers if any exist.** Rootsignal is the
   biggest. If there are smaller consumers (examples crate, tests,
   external libs), worth a glance.

## Honest meta-note

I committed v0.4 as `design-locked` without checking against
rootsignal. That was the same mistake as the 0.2.0 "airtight" claim —
declaring completeness before verifying. The plan was sketched against
my mental model of how a clean event-sourcing library should look,
not against how the production consumer actually uses the library.

Rootsignal being pre-launch gives us slack to refactor both sides,
which is the right answer. But the v0.4 plan shouldn't have claimed
lock-in before this audit.

For future plans: design-lock requires either (a) audit against
real consumers first, or (b) explicit "no consumers exist yet,
locking is provisional" marker.
