# v0.4 design — pressure test

The plan has been through three revision rounds, an audit, and a deep-
dive. This document attacks it adversarially from angles those passes
didn't cover, to surface remaining holes before implementation starts.

Categories of attack:
1. Type system edges
2. Migration corner cases
3. Kurrent alignment — where it might actually break
4. Backend implementation complexity
5. Performance characteristics
6. Operational scenarios (real production incidents)
7. Testing story
8. Versioning future / extensibility
9. Subtle semantic traps

Findings are rated: **HIGH** (must address before implementation),
**MEDIUM** (address during implementation, not blocking design),
**LOW** (note in docs, future work).

---

## 1. Type system edges

### F1.1 — `Apply<F>` orphan rule with foreign Fact types (LOW)

The Rust orphan rule says you can implement `Apply<F>` for type `A`
only if at least one of `A` or `F` is local to your crate.

Production scenario: rootsignal-scout has `PipelineState` (local).
It implements `Apply<F>` for facts from many domains (`SignalEvent`,
`ScrapeEvent`, etc.). These facts are in the same crate so this
works.

But: what if a third party crate `causal-search` defines its own
`SearchIndexState` aggregate and wants to implement `Apply<F>` for a
fact in `rootsignal-scout::events`? The orphan rule blocks this —
neither type is local to `causal-search`.

**Likelihood**: moderate. Cross-crate aggregates are a real pattern
in larger ecosystems.

**Mitigation**: document the orphan rule constraint. Workaround:
foreign-fact users define a wrapper enum in their crate and convert.
Same constraint exists today with the legacy `Apply<E>` trait, so
this isn't a regression.

**Verdict**: LOW — pre-existing Rust constraint, documented, not new.

### F1.2 — Generic Fact types (MEDIUM)

What if someone wants `enum SchedulingEvent<T: SomeTrait>`? The
trait def `Fact: 'static` requires concrete types. The `CATEGORY`
const would be problematic across generic instantiations — each
`SchedulingEvent<String>` and `SchedulingEvent<Uuid>` would have the
same CATEGORY const, but they're different Rust types.

**Likelihood**: low. Event sourcing typically uses concrete types
since events are serialized.

**Mitigation**: document that generic Fact types are unsupported.
The macro can reject them with a helpful error.

**Verdict**: MEDIUM — should be caught by macro and produce a clear
error, not a confusing trait-bound failure.

### F1.3 — `engine.load<A, F>` requires both type params (MEDIUM)

```rust
let (schedule, version) = engine.load::<Schedule, ScheduleEvent>(id).await?;
```

Two type params is verbose. The compiler can't infer F from A
because A may implement `Apply<F>` for multiple F (the cross-domain
accumulator case).

**Likelihood**: hits every command-handler call site.

**Mitigation**: option 1 — accept the verbosity. Option 2 — add a
marker trait `LoadableAggregate: Aggregate + Apply<Self::Fact>` with
`type Fact: Fact`, providing single-type-param `engine.load::<A>(id)`
ergonomics. Blanket impl: `impl<A: Aggregate + Apply<F>, F: Fact>
LoadableAggregate for A where A has exactly one Apply impl` — but
Rust can't express "exactly one" at the type level.

Most ergonomic: user opts in by implementing `LoadableAggregate`
manually (or via macro) for single-Apply aggregates:

```rust
impl LoadableAggregate for Schedule {
    type Fact = ScheduleEvent;
}
// Then:
let (schedule, version) = engine.load::<Schedule>(id).await?;
```

PipelineState (multi-Apply) doesn't implement `LoadableAggregate`
— `engine.load::<PipelineState>(id)` would be a compile error.
Correct semantics; clean ergonomics.

**Verdict**: MEDIUM — add `LoadableAggregate` trait or accept the
verbosity. Decide during P2 implementation.

### F1.4 — `Aggregator::for_type::<A>()` enumeration via macro (MEDIUM)

The constructor needs to know which `Apply<F>` impls exist for A.
Rust doesn't support compile-time impl enumeration without macros.

Options:
- a) Macro generates `for_type::<A>()` — but then macro must know
  every Apply impl that exists, which means they must be in the
  same macro invocation
- b) `inventory` crate — registers Apply impls via a static
  initializer; `for_type` reads the registry. Adds a dependency
  and "spooky action at a distance."
- c) Explicit constructor — user writes
  `Aggregator::new::<A>().with_apply::<SignalEvent>().with_apply::<ScrapeEvent>()` etc.
  Verbose but explicit.

**Likelihood**: every multi-Apply aggregate needs this.

**Mitigation**: combination — provide both the macro (for users who
opt in) and the explicit builder (for users who don't). The macro
is sugar over the builder.

**Verdict**: MEDIUM — decide between (a) and (c) during P2/P6
implementation. Probably (c) with macro sugar.

### F1.5 — `EmitInput::Many(Vec<Box<dyn FactErased>>)` heterogeneous? (MEDIUM)

The plan says `engine.emit(vec![f1, f2])` for batch. If `f1` and
`f2` are the SAME Fact type, `Vec<F>` works. If they're DIFFERENT
Fact types, `Vec<Box<dyn FactErased>>` is needed.

Today's `engine.append::<A>(id, expected, Vec<F>)` is homogeneous —
all facts in the batch must be the same type. Does v0.4 preserve
this constraint?

Production check: rootsignal batches multiple variants of the SAME
enum (e.g., `vec![SchedulingEvent::Triggered, SchedulingEvent::CadenceAdjusted]`).
Enum variants are the same type. Homogeneous works.

Cross-enum batches? `vec![ScheduleEvent::Triggered, RunEvent::Started]`?
Different Fact types, different streams, different CAS guards.
**Doesn't make sense** for `.expecting()` because each fact targets
a different stream. The plan's batch API should be homogeneous.

**Mitigation**: type `EmitInput` as generic over Fact:
```rust
pub fn emit<F: Fact>(&self, input: impl Into<EmitInput<F>>) -> EmitBuilder<'_, F>;
pub enum EmitInput<F: Fact> { One(F), Many(Vec<F>) }
```

This enforces homogeneity at compile time.

**Verdict**: MEDIUM — clarify during P5 implementation. Generic
EmitInput<F> is the right call.

## 2. Migration corner cases

### F2.1 — Existing rootsignal events with `"namespace:name"` event_type (HIGH)

Rootsignal's current event_type strings in the log are like
`"scheduling:schedule_created"`. Under v0.4, the runtime composes
event_type as `format!("{}:{}", CATEGORY, name())`.

For ScheduleEvent (CATEGORY="schedule") with `name() = "created"`:
- v0.4 composed: `"schedule:created"`
- v0.3 stored: `"scheduling:schedule_created"`

**The strings don't match.** Existing log data is unreadable under
v0.4 unless we either:
- a) Migrate the log (rewrite event_type column)
- b) Keep the v0.3 format and have name() return `"schedule_created"`
   so the composed string is `"schedule:schedule_created"` — still
   doesn't match `"scheduling:schedule_created"`
- c) Provide a "legacy event_type translator" in the backend that
   reads old-format events and presents them as new-format

Rootsignal is pre-launch, so option (a) is acceptable: write a
one-shot migration that rewrites all event_type strings.

**Likelihood**: 100% — every pre-existing event needs translation.

**Mitigation**:
- Pre-launch rootsignal: migration script during P12
- For other consumers: document the breaking change loudly; provide
  a migration recipe

**Verdict**: HIGH — needs explicit migration story for any consumer
with pre-existing log data.

### F2.2 — Stream name format change for split categories (HIGH)

LifecycleEvent and ScrapeEvent both target `scout_run-{id}` streams
today. Under v0.4 with category-only subscription, they split into
`lifecycle-{id}` and `scrape-{id}` streams.

Existing events are stored under `aggregate_type="scout_run"`.
After migration:
- Lifecycle events need `aggregate_type="lifecycle"`
- Scrape events need `aggregate_type="scrape"`

How do we know which is which when migrating? By event_type:
events with `event_type LIKE 'lifecycle:%'` → "lifecycle" category,
etc.

**Likelihood**: 100% for rootsignal.

**Mitigation**: migration script (P12) rewrites both `event_type`
and `aggregate_type` columns. Cleanup script verifies no events
remain under old categories.

**Verdict**: HIGH — but tractable since pre-launch.

### F2.3 — Cursor positions persist across migration (HIGH)

The CheckpointStore stores cursor positions per consumer. After
migration, the underlying log has the SAME positions but the
event_type strings have changed.

A consumer's cursor at position 1000 today, post-migration, still
sees the events at positions 1-1000 — just with different
event_type strings. The consumer's body MUST handle the new strings.

Concrete failure mode: consumer X with cursor at position 500
restarts post-migration. It reads event at position 501 with
event_type `"schedule:created"` (new format). It tries to
deserialize as `ScheduleEvent::Created` (which expects this format).
Works.

But: consumer Y with cursor at position 500 might have ALREADY
processed an event at position 400 that used to be event_type
`"scheduling:schedule_triggered"` (old format). Position 400 was
already past for Y; it doesn't re-read. So the migration is
forward-only safe.

**Likelihood**: 100% for any in-place migration.

**Mitigation**: deploy in this order:
1. Stop all consumers
2. Run migration script (rewrite event_type + aggregate_type)
3. Deploy v0.4 code with new Fact impls
4. Start consumers — they resume from their cursors with new
   event_type format

**Verdict**: HIGH — needs an explicit deploy runbook. Cannot do a
rolling deploy.

### F2.4 — GROUP_NAME collisions across renames (MEDIUM)

P4 moves GROUP_NAME to trait consts. Rootsignal's current
registration: `with_materializer(SchedulesMaterializer, "schedules")`.
After P4: `const GROUP_NAME: &'static str = "schedules";` on the
trait impl.

If rootsignal later renames `SchedulesMaterializer` → `SchedulesProjector`
during P12 (the rename phase), the GROUP_NAME stays the same string
("schedules"). The cursor in the CheckpointStore is still keyed by
"schedules". Resume cleanly.

**But:** if someone accidentally changes the GROUP_NAME during the
rename (e.g., to match the new struct name), the cursor resets to 0
and the consumer reprocesses the entire log.

**Likelihood**: moderate — easy mistake to make during rename PR.

**Mitigation**: P12 PR description must call out "GROUP_NAME values
MUST match the strings passed to with_materializer in v0.3". Add a
test fixture that verifies cursor continuity across the migration.

**Verdict**: MEDIUM — preventable with discipline + a verification
test.

### F2.5 — `engine.append::<A>(id, ver, Vec<F>)` → `emit(vec![]).expecting(ver)` doesn't exist in rootsignal (LOW)

The plan claims this migration is mechanical. Audit: rootsignal has
ZERO `engine.append::<A>` call sites. The legacy code uses
`engine.with_aggregator` to register OCC, but no one actually
CAS-writes.

So this migration is trivial for rootsignal: no work needed.

**Verdict**: LOW — already verified.

## 3. Kurrent alignment — where might it break?

### F3.1 — `MultiProjector::CATEGORIES` doesn't map cleanly to Kurrent (MEDIUM)

The plan says MultiProjector maps to "multiple `$ce-X` subscriptions
or `$all` with filter." But Kurrent's persistent subscription model
has a strict `(stream_name, group_name)` pair — one subscription per
pair.

Mapping options:
- **a) N subscriptions, one per category**: each subscription has
  its own group cursor in Kurrent. The runner merges by commit
  position. Problem: each subscription advances independently;
  exposing one `GROUP_NAME` is misleading.
- **b) One `$all` subscription with category filter**: one cursor,
  cleanly groups N categories. But Kurrent's `$all` filter is a
  prefix match on `category-*` stream names; works.

Option (b) is the right Kurrent mapping. The future
`KurrentEventLogBackend` MultiProjector impl uses `$all` with
filter, not multiple `$ce-X` subscriptions.

**Likelihood**: hits us when implementing the Kurrent backend.

**Mitigation**: document the chosen mapping; backend impl is single-
subscription with filter.

**Verdict**: MEDIUM — flagging now so the Kurrent backend impl
doesn't pick the wrong option.

### F3.2 — `$by_event_type` requires opt-in (LOW)

Kurrent's `$et-{event_type}` system streams are populated by the
`$by_event_type` system projection, which is disabled by default.
If someone runs a Kurrent backend without enabling it, event_type
subscriptions don't work.

v0.4 doesn't use event_type subscriptions directly — it uses
category subscriptions via `$ce-{category}` (populated by
`$by_category`, also disabled by default).

So: deploying the Kurrent backend requires enabling at least
`$by_category` on the Kurrent server. Document.

**Verdict**: LOW — operational note, not design issue.

### F3.3 — Kurrent's CAS uses event count, not version (LOW)

Kurrent's `expected_revision` parameter is the **count of events
in the stream**, not a separate version number. So:
- Empty stream: expected = `NoStream` or `None`
- 5 events: expected = `Exact(4)` (zero-indexed) or `StreamRevision(5)`

Causal-rs's `StreamVersion` is similar but uses 1-indexed positions
typically. Backend translation: subtract 1 when calling Kurrent's
gRPC API.

**Likelihood**: implementation detail; hidden by the backend.

**Mitigation**: document `StreamVersion` semantics (1-indexed,
inclusive); backend translates.

**Verdict**: LOW — implementation concern, not API concern.

## 4. Backend implementation complexity

### F4.1 — Postgres backend must atomically advance + write in P5 emit (MEDIUM)

Under v0.4's emit:
```rust
engine.emit(fact).expecting(version).await?;
```

Must:
1. SELECT version of `{CATEGORY}-{stream_id}` stream
2. If it doesn't match `version`, fail with conflict
3. INSERT the event
4. Return the new LogCursor

All atomic in one transaction. The Postgres backend wraps in `BEGIN ... COMMIT`
with `SELECT ... FOR UPDATE` on the stream's version row.

**Likelihood**: implementation detail. Already done in v0.3 backend
for `append`.

**Verdict**: MEDIUM — straightforward port from v0.3 append to v0.4
emit; no new design.

### F4.2 — Snapshot during multi-apply aggregate handling (MEDIUM)

P9 adds `snapshot_every(N)`. Multi-Apply aggregates (PipelineState)
aren't backed by a single stream, so they can't be snapshotted in
the standard sense (snapshot + replay-from-snapshot).

Plan says: only snapshot single-Apply aggregates.

But how does the engine KNOW which is which? At runtime, it's the
count of Apply impls. The macro-generated `Aggregator::for_type`
captures this; the engine reads it.

**Mitigation**: `Aggregator` value carries an `is_loadable: bool`
flag. Engine snapshot loop checks the flag.

**Verdict**: MEDIUM — straightforward; flag in registry.

### F4.3 — Backend impl for v0.4 EventLogBackend interface (LOW)

EventLogBackend in v0.4 takes `category: &str` and `stream_id: Uuid`
(separate args) for `load_stream`, replacing v0.3's
`(aggregate_type: &str, aggregate_id: Uuid)`. Same shape, renamed
args. Backend impl changes are nominal.

**Verdict**: LOW.

## 5. Performance characteristics

### F5.1 — `engine.load` cost on long streams (MEDIUM)

`engine.load::<A, F>(id)` reads the full stream `{F::CATEGORY}-{id}`
from position 0 and folds. For a stream with 10,000 events: 10,000
sequential I/O ops in the worst case.

Snapshots mitigate this (load latest snapshot + fold events past
snapshot). But snapshots are opt-in via `snapshot_every(N)`. Without
them, command handlers on long-running streams experience O(N) load
latency.

**Likelihood**: real production concern for any aggregate that lives
for thousands of events.

**Mitigation**:
- Document the linear-in-stream-length cost of `load` without
  snapshots
- Make snapshot_every easy to use (it is)
- Future: lazy projection-based load (use a projection's
  materialized state instead of folding the stream)

**Verdict**: MEDIUM — documented limitation, mitigated by snapshots.

### F5.2 — MultiProjector with N categories scans events from N streams (MEDIUM)

For a MultiProjector with `CATEGORIES = ["a", "b", "c", ...]`, every
batch poll has to scan events across N stream categories. In
Postgres: `WHERE aggregate_type IN (...)` with N items. Index
support for `IN` queries is generally good; with 10-15 categories,
this is fine.

But: at 100+ categories, query performance degrades. Unlikely in
practice (no one has 100 bounded contexts).

**Verdict**: MEDIUM — document the practical limit (~30 categories
per MultiProjector); split into multiple MultiProjectors beyond
that.

### F5.3 — `with_default_metadata` cost on every emit (LOW)

Every emit clones the default metadata map and merges per-emit
overrides. With `run_id` + `schema_v` as defaults (typical),
this is ~50 bytes copied per emit. Negligible.

**Verdict**: LOW.

## 6. Operational scenarios

### F6.1 — Pausing a projector that's behind doesn't help fast (MEDIUM)

`engine.pause_projection("X")` sets a flag in `ProjectionOps`.
The runner checks the flag before each batch poll. If the projector
is mid-batch when pause is called, the current batch completes,
then the runner stops.

For a slow projector with batch_size=1000 and 100ms per event, this
means up to 100 seconds before pause actually takes effect.

**Likelihood**: ops scenario when fixing a misbehaving projector.

**Mitigation**:
- Document: pause is "soft" — completes current batch then stops
- Future: smaller batch sizes when pause is requested
- Workaround: kill the process entirely, restart with the projector
  paused on the next run

**Verdict**: MEDIUM — document the soft-pause semantics.

### F6.2 — Resetting a projector while another consumer reads (HIGH)

`engine.reset_projection("X", LogCursor::ZERO)` sets cursor to 0.
The runner starts replaying from the beginning.

**But:** what if X's projector writes to a shared table that
another consumer Y is also reading from? Y might see partial
re-replay state.

This is a classic event-sourcing replay hazard. The mitigations are
application-side:
- Use blue-green tables (X writes to v2 table; promote when done)
- Use idempotent UPSERTs (replay doesn't corrupt state)
- Coordinate downtime explicitly

**Likelihood**: real in production.

**Mitigation**:
- Document: reset triggers full replay; coordinate with downstream
  consumers
- Recommend `causal_replay::ProjectionStream::Mode::Replay` with
  staged → active promotion as the safe replay mechanism (already
  exists in the library!)

**Verdict**: HIGH — must be documented loudly. Reset is a footgun.

### F6.3 — DLQ replay (LOW)

`engine.list_projection_failures(id, limit)` returns DLQ rows.
`engine.delete_projection_failure(id, event_id)` removes one.
Operator workflow: fix the bug, delete DLQ row, reset cursor to
before the failed event, let the projector retry.

This requires manual cursor manipulation: reset to the position
BEFORE the failed event. But `LogCursor` is global, not per-event-
in-stream. Determining "position before event X" requires reading
the event's log_position from somewhere.

**Mitigation**: `ProjectionFailure` already carries `event_id`; we
could also store `log_position` to make replay easier. Add the field
during P8.

**Verdict**: LOW — small enhancement to ProjectionFailure type.

### F6.4 — Consumer that's been stopped for a long time (MEDIUM)

If a projector group_name has been stopped for weeks and the log
has grown by 1M events, restarting the consumer triggers a 1M-event
catch-up. The runner processes batches as fast as possible.

During catch-up:
- New events keep arriving (live writers don't stop)
- The consumer lags further behind in absolute terms (live position
  advances while catch-up processes)
- Eventually catches up if event rate < processing rate

If event rate > processing rate, the consumer never catches up.
That's a sizing/architecture problem.

**Likelihood**: real in production when consumers stop for ops
reasons.

**Mitigation**:
- Document the catch-up dynamics
- Surface lag metric (already in `ProjectionStatus`)
- Future: parallel partition processing for catch-up

**Verdict**: MEDIUM — documented; not a v0.4 blocker.

## 7. Testing story

### F7.1 — Testing a Projector in isolation (LOW)

```rust
let projector = SchedulesProjector::new(pool);
let event = ScheduleEvent::Created { /* ... */ };
let ctx = Ctx::test_default();  // helper
projector.project(&event, ctx).await?;
// Assert: row exists in DB
```

The `Ctx::test_default()` helper builds a minimal context for unit
testing. v0.3 already has this pattern in test fixtures. Carries
over cleanly.

**Verdict**: LOW.

### F7.2 — Testing a Reactor with aggregate state (MEDIUM)

```rust
let reactor = RunCompletion::new();
let ctx = Ctx::test_with_aggregate(&pipeline_state);
let trigger = LifecycleEvent::PhaseCompleted { /* ... */ };
let events = reactor.react(&trigger, ctx).await?;
assert_eq!(events, /* expected */);
```

The `Ctx::test_with_aggregate(&state)` helper makes `ctx.aggregate::<A>()`
return the test state. v0.3 test fixtures do this; v0.4 keeps the
pattern.

**Mitigation**: ensure the `Ctx` struct can be constructed in test
code with arbitrary aggregator state — pub(crate) field access or a
`Ctx::for_test(...)` constructor.

**Verdict**: MEDIUM — confirm during implementation that the test
helper is ergonomic.

### F7.3 — Integration testing with MemoryStore (LOW)

End-to-end tests use MemoryStore as a single struct implementing
all backend traits. v0.3 already supports this; v0.4 preserves.

**Verdict**: LOW.

## 8. Versioning future / extensibility

### F8.1 — Adding fields to Fact trait is breaking (MEDIUM)

If we ever need to add a method to Fact (e.g., `correlation_strategy()`),
every Fact impl breaks. Default impl mitigates but only for additive
changes.

The current Fact trait has 3 methods + 1 const. Stable for now.

**Mitigation**: design the trait to be complete-enough for the
foreseeable use cases. Use default impls liberally for any future
additions.

**Verdict**: MEDIUM — design discipline note. Avoid trait expansion.

### F8.2 — Adding a consumer trait (e.g., Replicator) (LOW)

Adding a new consumer trait alongside Projector/Reactor/MultiProjector
is additive — doesn't break existing code. Standard pattern:
new trait, new `with_*` method, new runner.

**Verdict**: LOW.

### F8.3 — Kurrent backend specific options (MEDIUM)

The Kurrent backend may need backend-specific configuration that
doesn't apply to Postgres (e.g., tombstone behavior, persistent vs
catch-up vs volatile subscription mode). v0.4's EventLogBackend
trait doesn't expose these.

**Mitigation**: backend-specific config lives on the backend
constructor (`KurrentEventLogBackend::new(/* config */)`). The
trait stays narrow.

**Verdict**: MEDIUM — note in the Kurrent backend plan; not a v0.4
trait concern.

## 9. Subtle semantic traps

### F9.1 — `ctx.aggregate::<A>()` panic when no aggregators registered (MEDIUM)

Today's behavior: `ctx.aggregate::<A>()` panics if A wasn't
registered via `with_aggregators`. The panic surfaces a config bug
at the call site.

v0.4 preserves this. But: the panic message must mention that
GROUP_NAME isn't the issue (aggregates don't have GROUP_NAME); the
issue is the aggregate registration.

**Mitigation**: clear panic message.

**Verdict**: MEDIUM — make sure the panic message is helpful.

### F9.2 — `Apply<F>` cycle (LOW)

What if an aggregate `A: Apply<F>` and `A.apply(&F)` mutates `self`
to a state that, when re-applied for the same F, infinite-loops? It
doesn't — apply is called once per event by the runtime; there's no
loop. Trait doesn't enable this footgun.

**Verdict**: LOW — not a real concern.

### F9.3 — `on_dlq` mapper called twice for the same failure (MEDIUM)

If a reactor's terminal failure triggers `on_dlq`, and the
DLQ-emitted Fact itself fails downstream, does the second failure
re-trigger `on_dlq`?

Depends on whether the DLQ fact's downstream IS a reactor (subject
to its own retry budget). If so, yes — DLQ events cascade.

This can create infinite DLQ loops if downstream reactors fail
indefinitely.

**Mitigation**:
- Document: `on_dlq` events should be terminal facts not consumed
  by reactors (i.e., emit to a category that has no reactor
  subscribers)
- Future: detect DLQ-of-DLQ and short-circuit (out of scope for
  v0.4)

**Verdict**: MEDIUM — document.

### F9.4 — `EmitInput::Many` batch order (MEDIUM)

For a batch emit, the order of facts in the Vec MUST be preserved
in the log. Today's append: yes. v0.4's emit: must preserve.

Consider: `engine.emit(vec![f1, f2, f3]).expecting(v).await?`.
Backend writes f1 at v+1, f2 at v+2, f3 at v+3. Same order as
input.

**Mitigation**: backend impl test — verify order preservation
across batches.

**Verdict**: MEDIUM — testable contract; verify during P5.

### F9.5 — Reactor returning Facts in `Events` from a different category (HIGH)

```rust
impl Reactor for RunCompletion {
    type Trigger = LifecycleEvent;
    async fn react(&self, trigger: &LifecycleEvent, ctx: Ctx<'_>) -> Result<Events> {
        Ok(events![ScheduleEvent::Created { /* ... */ }])  // ← different category
    }
}
```

The reactor consumes lifecycle events but emits schedule events.
Cross-category reactor outputs are legitimate and common.

The reactor outbox machinery (C12) writes the output through the
emit path. Under v0.4's category-only model:
- Output Fact's `CATEGORY = "schedule"` determines target stream
- Output goes to `schedule-{stream_id}` stream
- Stream id comes from `ScheduleEvent::Created::stream_id()`

No issue. The mechanism preserves category alignment regardless of
trigger category.

**But:** the reactor's effective behavior is "consume from
lifecycle category, write to schedule category." This is fine but
worth documenting — reactors are cross-category by design.

**Verdict**: HIGH — clarify in trait docs that reactors can emit
facts of any category, not just the trigger's.

### F9.6 — `Ctx::aggregate` consistency across batch (HIGH)

Within a Projector's `project()` call, `ctx.aggregate::<A>()`
returns state folded INCLUDING the current event being projected.

But: a Projector processes events in batches. If batch contains 5
events and the projector is on event 3, does `ctx.aggregate::<A>()`
reflect events 1-3 or events 1-2?

Today's v0.3 semantics: `curr` includes the current event; `prev`
is state before this event. So on event 3: prev = state after events
1-2, curr = state after events 1-3.

For a batch of 5 processed sequentially: each `project()` call sees
the prev/curr pair for its specific event.

**But:** does the runtime fold ALL 5 events into the aggregate state
before invoking project() for each, or fold one at a time
interleaved with project() calls?

Today's behavior: interleaved (apply fact → call project → repeat).
This means project sees its own event's prev/curr. Consistent.

**Mitigation**: document this interleaving. It's the only sane
behavior but easy to assume otherwise.

**Verdict**: HIGH — document carefully. Hidden semantics that
projects rely on.

## Net pressure-test outcome

The design holds up. Six HIGH-severity findings, all addressable
through documentation + migration scripts (not design changes).

The biggest exposure is the rootsignal migration story (F2.1-F2.3)
— event_type format change, stream-category rename, deploy
ordering. Pre-launch status makes this tractable but requires a
real runbook before P12 starts.

No findings invalidate any of the locked D1-D14 design decisions.
The trait shapes, naming, and Kurrent alignment all survive
adversarial review.
